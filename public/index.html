03 / CASE STUDIES

拆开看：三个项目的技术骨架

光看简介不够。这一节把社区里最有代表性的三个项目拆到架构层，你能直接抄走它们的做法。

案例 A · Baby Reachy-Mini Companion：把 7 个模型塞进婴儿房

179 个赞，作者 ravediamond。 目标很明确：婴儿哭了，机器人自己去安抚，然后给家长发一张照片。全程不联网、不调云 API、不依赖预写脚本—— 而是让一个视觉语言模型看着画面自己决定“现在该做什么”，通过工具调用去执行。

最值得学的一个设计取舍：作者在文档里坦言，小模型无法可靠地串联 3 个以上的工具调用， 所以“哭声告警”和“危险告警”这两条最关键的路径绕过大模型，直接由代码确定性地发出——大模型只负责“说什么”， 告警投递不交给概率。把可靠性要求最高的环节从生成式链路里摘出来，是这个项目最专业的一手。
另外它用了 profile 机制：每个 profile 有独立的 system prompt、工具集与人格，所以作者说换场景（自闭症辅助、老人陪伴、宠物监控、家庭安防）“是改配置，不是做工程”。 实测端到端延迟：Mac 约 6 秒，Jetson Orin NX 约 3 秒。

如果你要发布成“应用商店里能装的应用”，需要实现官方约定的 ReachyMiniApp 契约——只需实现一个 run()：

import threading, time
import numpy as np
from reachy_mini import ReachyMini, ReachyMiniApp
from reachy_mini.utils import create_head_pose


class MyApp(ReachyMiniApp):
    def run(self, reachy_mini: ReachyMini, stop_event: threading.Event):
        t0 = time.time()
        while not stop_event.is_set():
            t = time.time() - t0
            # 脑袋做 0.2Hz 正弦摆动
            head_pose = create_head_pose(yaw=30.0 * np.sin(2 * np.pi * 0.2 * t), degrees=True)
            # 两根天线反向摆，0.5Hz
            a = np.deg2rad(25.0 * np.sin(2 * np.pi * 0.5 * t))
            reachy_mini.set_target(head=head_pose, antennas=np.array([a, -a]))
            time.sleep(0.02)          # 50Hz 控制环


if __name__ == "__main__":
    app = MyApp()
    try:
        app.wrapped_run()
    except KeyboardInterrupt:
        app.stop()
关键约束：同一时间只能运行一个应用；应用运行在 daemon 的子进程里，不自己管硬件连接； 无线版上应用跑在共享虚拟环境 /venvs/apps_venv/；停止时 daemon 会发 SIGINT，所以要在循环里轮询 stop_event 优雅退出。 应用退出后机器人会回到默认姿态。

中国区实战：先解决网络，再谈玩法

这一节的每一条都出自官方 Troubleshooting / FAQ 文档，不是猜测。如果你刚组装完发现“应用商店打不开”“对话应用没反应”，八成不是硬件问题。

症状 1 · 应用商店列表转圈 / 装不上
换 Hugging Face 镜像端点
官方在 FAQ 里直接给出了镜像方案：把 HF_ENDPOINT 指向 https://hf-mirror.com/。原话还提醒「你可能还需要给 PyPI、GitHub 也配镜像」。
export HF_ENDPOINT=https://hf-mirror.com/
症状 2 · 对话应用连不上 / 一直不说话
实时语音接口在墙外
官方明确写了：对话应用依赖 OpenAI 的实时语音 API，在中国大陆可能无法访问。官方给出的最优解是在机器上做 VPN/代理，并推荐按域名分流而不是全局代理——只把 huggingface.co 与 api.openai.com 走代理。
症状 3 · 开了代理之后，机器人反而找不到了
把内网与 mDNS 排除掉
官方专门提醒：走代理时要把本地网段排除，否则 reachy-mini.local 会失联。需要放行的至少包括 192.168.0.0/16、127.0.0.1，以及端口 22（SSH）、8000（daemon）、5353 TCP/UDP（mDNS 本地发现）。
症状 4 · 无线版在机器人上改了环境变量却不生效
要给 daemon 服务本身加
SDK 支持标准的 HTTP_PROXY / HTTPS_PROXY / NO_PROXY，覆盖所有出网 HTTPS 请求（HF 登录、应用列表、应用安装更新、WebRTC 信令）。但在无线版上必须让 daemon 服务看到这些变量：sudo systemctl edit reachy-mini-daemon，在 [Service] 段里加，然后重启服务。
# ① 镜像：解决应用商店与模型下载慢
export HF_ENDPOINT=https://hf-mirror.com/

# ② 代理：只在需要时给需要的域名
export HTTPS_PROXY=http://127.0.0.1:7890
export HTTP_PROXY=http://127.0.0.1:7890
export NO_PROXY=localhost,127.0.0.1,192.168.0.0/16,reachy-mini.local

# ③ 无线版：让 daemon 服务也能看到（否则只有你的 shell 生效）
sudo systemctl edit reachy-mini-daemon
#   [Service]
#   Environment="HF_ENDPOINT=https://hf-mirror.com/"
#   Environment="HTTPS_PROXY=http://192.168.1.10:7890"
#   Environment="NO_PROXY=localhost,127.0.0.1,192.168.0.0/16,reachy-mini.local"
sudo systemctl restart reachy-mini-daemon

# ④ 验证还活着
ping reachy-mini.local
curl -s localhost:8000/api/daemon/status
代理分流的最小规则集：只代理 huggingface.co 与 api.openai.com；放行本地网段、22、8000、5353。 这样机器人既上得了网，又不会被代理“藏”起来——这是官方 FAQ 里推荐的做法。
好消息：官方在 FAQ 结尾写了一句「基于开放权重模型的方案正在路上」。 对国内用户来说，这意味着不依赖境外实时语音 API 的本地对话方案是官方明确的方向——而社区其实已经先跑出来了： 端侧极速反应（纯树莓派 CPU）、Baby 陪伴（Jetson 7 模型全本地）、NVIDIA Jetson 助手，都不需要连境外服务。 更关键的是，Hackaday 在 2026 年 6 月报道过社区跑通的全本地对话链路，其中 LLM 用的是 Qwen3-4B-Instruct—— 这意味着让 Reachy 用中文跟你对话、且完全离线，已经有现成可走的路。

10 / PATTERNS

把 80 多个项目摊开看，能看到这几个规律

这一节不是介绍单个应用，而是这套生态的“底层结构”。理解了它，你更容易想到自己该做什么。

① 云端大模型 vs 端侧小模型，是两条清晰的路

技术选型
  1. 云端派：官方对话应用、ElevenLabs、Gemini Live、Minder——把语音与推理交给托管服务，换来最好的对话质量，代价是联网与延迟。
  2. 端侧派：端侧极速反应（树莓派 CPU）、Baby 陪伴（Jetson 7 模型）、Reachy Claw（ASR+TTS 约 110ms）、NVIDIA Jetson 助手（Gemma 本地）——换来隐私、离线与确定性延迟，代价是要自己搭管线。
  3. 选哪条路，先回答一个问题：你更怕“不够聪明”，还是更怕“不可靠 / 不可用”？

② “不调用 LLM”是被反复验证的有效选择

反直觉但成立
  1. 点赞第二的 F1 解说员根本没用大模型：210 套字符串模板 + 一个规则引擎（兴奋等级 × 叙事视角 × 防重复追踪），效果足以拿到 207 个赞。
  2. 端侧反应应用用语义检索替代生成，把反应压到 100ms 以内。
  3. 结论：表达力来自动作设计与时机，不来自模型参数。先想清楚“要它做什么反应”，再决定要不要上大模型。

③ 芯片厂商把它当成边缘 AI 的展示台

一个容易被忽略的信号
  1. 生态里点赞第一（Phone Home）和两个技术标杆（3D 可视化、端侧反应）的作者，都隶属 Arm。
  2. NVIDIA 官方下场做了 Jetson 全本地助手，工程标准明显高于社区平均（SBOM、wheel 校验、拒绝静默降级）。
  3. 这说明 Reachy Mini 已经不只是一个玩具，而是被当作边缘 AI 的参考平台在用。

④ 9 个自由度，每个项目只用了其中一部分

设计上的克制
  1. F1 解说员只用颈部 6 个自由度，底座与天线不动。
  2. AirPlay 音箱只让天线打节奏——因为 Stewart 平台和底座电机会在音乐里发出声音，只有天线电机几乎无声。这是很典型的机器人产品思维。
  3. 反过来，ESP32 眼睛改装干脆绕开原厂所有灯光，自己做一套视觉通道。

⑤ 开源协议的边界，是这个生态的真实议题

想商用必读
  1. SDK 是 Apache-2.0，但硬件设计文件是 CC BY-SA-NC（禁止商用），完整 STEP 文件官方称“计划发布”但尚未放出。
  2. Phone Home 依赖的 Ultralytics YOLO 是 AGPL-3.0，作者专门加了 NOTICE 声明。
  3. AirPlay 音箱基于 shairport-sync 与 librespot，作者明确写了“非 Apple MFi 授权、未获 Spotify 官方授权”。
  4. 也有正面范例：ElevenLabs 应用的 emotion_detector.py 顶部完整标注了情绪触发方式源自 Pollen 官方项目并附源码链接。

⑥ 门槛最低的贡献方式，其实是“一件事做好”

给你的选题建议
  1. 点赞榜上不只有硬核项目：节拍器（天线当摆锤）、尤克里里调音器、天线敲击实验室、番茄钟 都只是把一件事做透。
  2. 最有画面感的选题往往最具体：“让机器人读实体绘本给孩子听”“手机一响它就瞪我”“冲浪预报念给我听”。
  3. 反向看：通用助手类应用已经有官方与多个商业版本，别从那里开始。

12 / FAQ

新手最常问的几件事

应用装在哪里？会不会把机器人搞坏？
应用由 daemon 以子进程方式启动，不直接碰硬件连接，也不改固件；退出后机器人回到默认姿态。无线版的应用装在 /venvs/apps_venv/ 这个共享虚拟环境里。 唯一要注意的是存储——无线版只有 16GB eMMC，装太多应用或缓存视频容易满，社区里有专门的“存储管家”应用可以清理。
没有实体机器人，能先玩吗？
可以，而且强烈建议先这样。官方 SDK 自带 MuJoCo 仿真：mjpython -m reachy_mini.daemon.app.main --sim。 社区还有纯浏览器的仿真器（Reachy Mini JS、Microduck + Reachy Simulator）以及不接机器人的 3D 可视化工具，写代码、调动作都用得上。
对话应用那么多版本，该装哪个？
先装官方对话应用建立基线，再按需求换：要长期记忆 + MCP 工具选 Gemini Live 版；要最好的音色与情感表达选 ElevenLabs 版；要隐私与离线选 端侧极速反应（它不做完整对话，但完全本地）；要在 Jetson 上全本地跑选 NVIDIA Jetson 助手。
能不能让它做我自己的事（比如看家、提醒、播报）？
能，而且这是社区最主流的玩法。两条路：① 基于官方对话应用 换 profile / 加工具（reachy-mini-app-assistant create --template conversation），适合“加一个新能力”；② 直接写控制环（set_target + 50Hz），适合“做一个新反应”。社区的 Phone Home、Receptionist、Minder、Astronomer 都是这两条路的产物。
性能上限在哪？能跑多大的模型？
取决于算力放在哪。无线版机载 CM4 只适合轻量端侧模型（Silero、Moonshine、MiniLM 这个量级）；Lite 版或无线版 + 外部电脑/Jetson 才能跑到 Whisper + VLM 甚至多模型流水线。社区的 Baby 陪伴项目用 Mac + Jetson Orin NX 跑了 7 个模型——这是目前公开案例里的上限参考。
怎么让我的应用出现在官方应用商店里？
发布到 Hugging Face Space，并在 README frontmatter 里加标签 reachy_mini_python_app（Python 应用）或 reachy_mini_js_app（浏览器应用）。 用 CLI 的 reachy-mini-app-assistant create --publish 会自动处理这些元数据。发布后，别人的机器人控制面板里就能看到你的应用并一键安装。
在中国大陆用，最容易卡在哪一步？
三个地方：① 应用商店与模型下载慢——把 HF_ENDPOINT 指向官方 FAQ 推荐的镜像；② 对话应用连不上——它依赖境外的实时语音 API，官方建议用 VPN/代理，且推荐按域名分流（只代理 huggingface.co 与 api.openai.com）；③ 开了代理机器人就失联——要把内网网段与 22 / 8000 / 5353 端口排除，否则 reachy-mini.local 找不到。详见上面第 08 节。 想彻底绕开网络问题，可以先用全本地方案：端侧极速反应（树莓派）、Baby 全本地陪伴（Jetson）、NVIDIA Jetson 助手。
社区在哪里？遇到问题去哪问？
官方 Discord（Pollen 社区）、Hugging Face 上各 Space 的评论区、以及 GitHub Issues。中文用户还可以看 Reachy Mini Developer Guide（HP 工程师写的实战踩坑指南）和官方的 Troubleshooting & FAQ 文档。
